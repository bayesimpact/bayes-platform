**Orchestration** lets a **conversation agent** hand off parts of a conversation to
other agents, called **sub-agents**. The main agent (the **orchestrator**) stays in
charge of the conversation, but when a request matches a sub-agent's specialty it
**delegates** to that sub-agent and folds the answer back into its reply.

Orchestration is configured in the editor of a **conversation agent** (a form agent
is one too), in **Studio**: **Orchestration** sits in the editor's left menu, under
**More**. It is not part of the agent's draft: it opens in a full page with its own
**Save**, and your changes apply to the agent **in production** as soon as you save
them. It has no versions in the [version history](/en/agent-version-history). It's an
optional feature: the entry only appears when your workspace has orchestration
enabled. Extraction agents don't have it.

> **Ask to have it enabled.** Orchestration is turned on per workspace. If your
> conversation agent's editor has no **Orchestration** entry under **More**, the
> feature isn't enabled for your workspace yet. Contact the Bayes team to request it.

## How orchestration works

- There's **no "make this an orchestrator" switch**. An agent becomes an orchestrator
  simply by having **one or more enabled sub-agents**. With none, the empty state
  reads *This agent answers directly without delegating to another agent.*
- Each sub-agent is exposed to the orchestrator's model as a **tool**, defined by a
  **Tool name** and a **Tool description**. On every turn, the model decides — based
  on those descriptions — whether to call a sub-agent, and with what task. So the
  **Tool description is what drives delegation**: write it to clearly state when the
  sub-agent should be used.
- A **sub-agent can be another conversation or form agent** in the same workspace.
  Extraction agents cannot be sub-agents. An agent can't be its own sub-agent, and an
  agent already added won't appear again in the available list.
- **Disabled** sub-agents stay configured but are not offered to the model. You can
  attach up to **20** sub-agents.
- A sub-agent runs with its **published** version. An agent that was never published
  carries a **Draft** badge in the list and is not offered to the orchestrator until it
  is published.

## Step by step

### 1. Open a conversation agent

In **Studio**, open the **conversation** agent you want to turn into an orchestrator
(from the **Agents** list in the left sidebar, or its card on the workspace
overview). Its page opens. You need permission to manage the agent.

### 2. Open the agent editor

At the top right of the agent's page, click **Edit**. The button shows what the editor
opens on: a **Draft** badge, or the published version (for example **v3**).

### 3. Open Orchestration

In the editor's left menu, under **More**, click **Orchestration** (it carries an
external-link icon: it opens over the editor). If you don't see it, the feature is
either not enabled for your workspace or you're not on a **conversation** agent (see
Troubleshooting).

### 4. Read the starting point

**Orchestration** opens in a full page. Its header reads *These settings are not part
of the draft: they apply in production as soon as you save.*, with **Close** and
**Save** at the top right (they also show at the bottom of the page). The page has two
sections:

- **Sub-agents** (top) — the agents this orchestrator delegates to. Before you add
  any, it shows an empty state: **No sub-agents** / *This agent answers directly
  without delegating to another agent.*
- **Available conversation agents** (below) — the agents you can attach.

### 5. Add a sub-agent

Under **Available conversation agents**, each candidate is shown as a card with its
**name** and its instructions. Click **Add** on the one you want to delegate to. It
moves up into the **Sub-agents** list with sensible defaults, and disappears from the
available list. An agent that was never published shows a **Draft** badge: you can
add it, but the orchestrator only uses it once it is published.

> The list holds your other **conversation and form** agents. If there are none, it
> reads **No other conversation agents are available.** — create a conversation or
> form agent first (extraction agents aren't eligible).

### 6. Configure the sub-agent

Each attached sub-agent has three fields:

- **Tool name** — the identifier the model calls, pre-filled as `ask_<agent name>`
  (placeholder **ask_specialist_agent**). It may contain only letters, numbers,
  underscores and hyphens, 1–64 characters.
- **Tool description** — pre-filled as *Route specialized requests to `<name>`.* This
  is the most important field: the orchestrator's model reads it to decide **when** to
  delegate, so describe the sub-agent's specialty precisely (up to 2000 characters).
- **Mode** — how the orchestrator uses the sub-agent:
  - **Consulted** (default): the orchestrator calls the sub-agent for one exchange and
    answers the user itself. Right for an expert you ask a question to.
  - **Takes over**: the sub-agent talks to the user directly, in the same conversation,
    until its part is done, then hands the conversation back. Right for a form or an
    interview the sub-agent must lead itself. The session header shows who the user is
    talking to, and each reply names the agent that wrote it.

### 7. Enable, disable, or remove

Each sub-agent row shows an **Enabled** / **Disabled** badge and a **Switch**:

- Turn the **Switch** off to keep the sub-agent configured but stop offering it to the
  model; turn it on to make it available again.
- Click the **trash** icon (**Remove**) to detach it entirely — it returns to the
  **Available conversation agents** list.

### 8. Save

Click **Save**, at the top or at the bottom of the page. The button stays greyed out
until you've made a change, and the whole set of sub-agents is saved together. Once
you've changed something, **Close** becomes **Cancel**. Cancel, the close cross,
Escape or a click outside the page with unsaved changes opens the **Unsaved changes**
dialog, which asks whether to **Discard** them.

### 9. Confirm

The **Apply these settings now?** dialog reads *These settings do not go through the
draft: they apply to the agent **in production** as soon as you save.* Click **Save**
to apply them, or **Cancel** to go back to the page. Pressing Enter in a field asks for
the same confirmation.

## What happens at runtime

When a user talks to the orchestrator, the model sees each **enabled** sub-agent as a
tool (named by its **Tool name**, explained by its **Tool description**). It decides
on its own whether to call one — handing it a task and relevant context — then uses
the sub-agent's answer to compose its reply. Conversation sub-agents reply directly;
form sub-agents run their form flow. Delegation is driven entirely by the tool
descriptions, so clear descriptions produce better routing.

A sub-agent in **Takes over** mode changes who speaks. When the orchestrator hands the
conversation over, it writes one sentence of transition and the sub-agent asks its first
question right away, in the same reply. The user's next messages go to the sub-agent
until it judges its part complete; the orchestrator then resumes on its own, without a
message from the user. A sub-agent that filled a form is not handed the conversation a
second time: the orchestrator uses what it collected instead. The orchestrator is told what
each sub-agent collected and whether it is done, and a sub-agent that takes over is told what
earlier sub-agents already collected, so the user is not asked the same question twice. A
sub-agent that ends its part without saying so explicitly is still handed back: the platform
reads its last reply for a conclusion. When a form sub-agent concludes, the platform reads its
part of the conversation once more and fills in the fields the exchange left empty, without
changing an answer already recorded.

## Tips

- Invest in the **Tool description** — vague descriptions lead to missed or wrong
  delegations.
- Give each sub-agent a distinct, readable **Tool name** (e.g. `ask_billing`,
  `ask_scheduling`) so runs are easy to recognise.
- **Disable** a sub-agent instead of removing it when you only want to pause it — its
  configuration is preserved.
- Use a **form** sub-agent when the specialised task is to collect structured
  information, and a **conversation** sub-agent for question-answering.

## Troubleshooting

- **I don't see Orchestration in the editor** — it appears under **More** only for
  **conversation** agents (form agents included), only when the workspace has
  orchestration enabled, and only if you can manage the agent. Extraction agents never
  show it.
- **My sub-agent changes are live but not in the version history** — that is
  expected: orchestration is not part of the draft and has no versions. Restoring a
  version does not change the sub-agents.
- **A sub-agent with a Draft badge is never called** — it was never published. Open
  that agent's editor, then **Manage versions** and **Save version**.
- **No agents in Available conversation agents** — the message **No other conversation
  agents are available.** means there are no eligible agents. Create another
  **conversation** or **form** agent first; extraction agents and the agent you're
  editing don't appear.
- **Save fails on the tool name** — tool names accept only letters, numbers,
  underscores and hyphens and must be 1–64 characters (the error message is in
  English). Fix the name and save again.
- **My sub-agent is never used** — check its **Switch** is **Enabled**, and make its
  **Tool description** more specific about when it should handle a request.
- **Related:** sub-agents are ordinary agents — see
  [Add a conversation agent](/en/add-a-conversation-agent) to create the agents you
  delegate to.
